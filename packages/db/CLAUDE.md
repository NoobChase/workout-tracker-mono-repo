# packages/db

The Drizzle schema, its migrations, the query helpers every layer shares, and
the standard exercise catalog. Procedures: `schema-change` and `neon-branch`
skills (root `CLAUDE.md`).

## Layout

- `src/schema.ts` — **the** schema file and the source of truth for every table,
  plan and session side. Its header lists the one thing it cannot say: four
  uniques (the `workouts`, `planned_exercises` and `session_exercises`
  positions, the `session_sets` set number) are `DEFERRABLE` via custom
  migrations.
- `migrations/` — generated by `npm run generate`. Never edited by hand; never
  rewritten once applied anywhere. `0001` and `0005` are the sanctioned
  `--custom` ones.
- `src/scope.ts` — the user-scoping primitives. **Every user-facing query goes
  through these.**
- `src/users.ts` — identity: `resolveUser` (select first, upsert on a miss),
  `softDeleteUser`, `isPro`. The only code keyed on `clerk_user_id`.
- `src/catalog.ts` + `src/seed.ts` — standard exercises as data, and the
  idempotent seed. `scripts/seed.ts` is the CLI CI runs.
- `src/client.ts` — `createDb(pool | poolClient)`. WebSocket driver only.
- `src/predicates.ts` — `countsAsSet`, the one "a set that counts" condition
  (`parent_set_id IS NULL AND kind <> 'WARMUP'`). Every count, chart, PR and
  progression query over `session_sets` `and()`s it in. Never retype it.
- `src/clone.ts` — `clonePlan(tx, userId, { sourcePlanId, target, ids? })`,
  the clone primitive (operations.md §0.2) for all three callers: a new cycle
  row (`{ programId, newPlanId, cycleNumber }`) or an existing plan's subtree
  replaced (`{ existingPlanId }`). Returns the old → new id maps; passing them
  back as `ids` makes a rerun write nothing.
- `src/fingerprint-core.ts` — the one cycle normalizer, pure (no Drizzle, no
  database; `node:crypto` only), also exported as
  `@workout-tracker/db/fingerprint` for non-database processes such as the web
  e2e fake API. `cycleFingerprint(tree)` is the SHA-256 of a cycle's authored
  content (operations.md §3.8: notes excluded, group keys renumbered, numerics
  normalized to their column's scale); `cycleContentKey(tree)` is the same
  normalization with every workout, slot and set `notes` included;
  `canonicalJson` is its key-sorted JSON. Input type: `FingerprintInput`.
- `src/fingerprint.ts` — `readCycleTrees` / `storedCycleFingerprints`, which
  read stored cycles through `userScope`, one query per level, as
  `StoredCycleTree`: the `packages/shared` cycle-tree wire shape (every column
  present, numerics as numbers). Re-exports the core. A migration to
  `workouts` or `planned_*` updates both.
- `src/templates.ts` — `TEMPLATES`, the starter programs as data, like the
  catalog: frozen slugs, catalog ids, sets and rep ranges, no weights.

## Scoping

- `userScope(user.id).<table>` is the `where` (or one arm of an `and()`) for
  any read, update or delete of a user-owned table. Never an inline
  `WHERE user_id = ...` — most tables have no `user_id`; they reach it up the
  ownership chain, and the helper knows the chain.
- Before inserting under a parent — a planned exercise into a workout, a
  session at a workout — `assertOwned(tx, userId, table, ids)` inside the same
  transaction. A foreign key proves the parent exists, not whose it is.
- Any exercise reference from user data: `assertExercisesUsable` (standard or
  the user's own, never another user's private exercise).
- `assertOwned`'s doc comment lists which check each session reference needs.
  After an `ON CONFLICT (id) DO NOTHING` insert of a client-minted id, re-read
  the row through `userScope`: a collision with another user's id "succeeds"
  silently otherwise.
- A new user-owned table gets its condition in `userScope` and `OwnedTable`
  **in the same change**, plus a case in `test/scope.test.ts`.
- `UserId` is branded; only `resolveUser` produces one. Casting a string to it
  outside a test is a smell.

## Catalog

Edit `src/catalog.ts`, nothing else. Ids are frozen UUIDv7 literals; retire
with `isActive: false`, never delete an entry. The `schema-change` skill has the
full rules. CI seeds after every migration; never run `npm run seed` against
`dev` or `production` by hand.

## Tests

`npm test -w @workout-tracker/db` creates a Neon branch off `dev`, migrates it,
runs everything in `test/`, and deletes it (`scripts/with-test-branch.sh`).
Locally that needs `neon auth`; CI uses the API key from SSM.

- `inRolledBackTransaction` + `createDb(client)` for anything that can live in
  one transaction. Deferred constraints only fire at `COMMIT`, which never
  happens there — `SET CONSTRAINTS ALL IMMEDIATE` to test one.
- Tests that need several connections (races) commit for real: use
  `seed_`-prefixed `clerk_user_id`s and delete the rows in `after`.
- Firing calls with `Promise.all` does **not** reproduce a race here: each opens
  its own WebSocket and setup serialises them. Force the interleaving with an
  open transaction, as `test/users.test.ts` does.
- `xmin` is the cheap proof that a statement wrote nothing.
- `test/clone.test.ts` commits for real, since a rerun is a second
  transaction. It deletes sessions and programs before users, rather than
  trusting one cascade to remove plan rows before the private exercise they
  `RESTRICT`.

## drizzle-kit

`generate` asks interactively when a change looks like a rename (a column
dropped and another added on one table) and fails without a TTY. Split the
change into two schema edits and generate twice — see migrations `0002`/`0003`.
Name migrations with `npx drizzle-kit generate --name <what_it_does>`.
